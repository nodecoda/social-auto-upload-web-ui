# 九、关键设计决策与技术债

## 9.1 关键设计决策

### D1. Registry 模式平台扩展

**决策**：用 `platform_id → class` 注册表替代硬编码 if/else 分发。
**收益**：新增平台只需实现 BasePlatform 子类并在注册表添加一行。
**代价**：注册表需要手动维护（`_populate_registry` 内的 imports 列表），未使用装饰器自动发现。

### D2. 任务队列基于 asyncio + 后台线程

**决策**：Flask 同步 WSGI 不适合长任务，采用「后台线程运行 asyncio 事件循环 + ThreadPoolExecutor 执行同步发布函数」。
**收益**：并发控制简单（max_concurrent），状态机清晰（QUEUED→RUNNING→SUCCESS/FAILED）。
**代价**：线程与事件循环混合模型复杂；waitress 多线程 + 发布函数的浏览器操作无法真正并行（浏览器操作本身是异步但被包在 executor 里）。

### D3. 重试机制禁用

**决策**：任务失败立即 FAILED，不做自动重试。
**原因**：视频上传是长耗时、有副作用操作（可能实际上传成功但返回失败），自动重试会导致重复上传。
**代价**：瞬时网络抖动导致失败需要用户手动重试。

### D4. Payload 透传（新） vs myUtils（旧）双路径

**决策**：`task.payload` 非空时直接 `platform.publish_video(**payload)`；空时走旧 `myUtils.postVideo` 函数。
**原因**：平滑过渡到新平台实现，兼容历史任务。
**代价**：两套代码路径并存，维护成本增加（旧路径最终应删除）。

### D5. 本地优先 + 同源部署

**决策**：数据全部本地存储，生产模式 Flask 单端口托管前端。
**收益**：部署简单、隐私好、无服务器成本。
**代价**：无法多用户共享；所有自动化在本地浏览器执行。

### D6. CloakBrowser 隐身浏览器

**决策**：用 CloakBrowser 替代标准 Playwright 默认浏览器。
**原因**：规避平台机器人检测（navigator.webdriver 等）。
**代价**：额外二进制下载、版本兼容风险、无头/有头模式复杂度。

### D7. cookie 导入标准化

**决策**：基类提供统一的 4 步 import_cookie 流程，平台只需实现 `_parse_cookie_to_storage_state`。
**收益**：避免每个平台各自实现导入逻辑。
**代价**：部分平台存储 state 结构差异需逐个适配。

## 9.3 可改进方向

1. **流式上传**：大文件 path-based 流式写入，避免 OOM
2. **统一 DB 访问层**：封装 sqlite 连接上下文管理、事务、迁移版本
3. **平台自动化健壮性**：元素等待策略、失败截图、DOM 变更自愈
4. **任务队列持久化**：队列存 Redis/文件，进程重启可恢复
5. **发布幂等性**：任务 ID 幂等键，防止重复发布
6. **前端状态持久化**：分片/批次状态存入 localStorage/IndexedDB
7. **多用户/多机协作**：可选中央服务模式（当前纯本地）
8. **资源清理**：cookies/ 旧目录、废弃表（file_records）、过期 upload_chunks 定期清理
9. **统一错误码**：前端目前依赖 code 字段，各蓝图返回格式不完全一致（200/201/203 混用）
10. **MCP 鉴权强化**：支持 API Key 轮换、过期时间
